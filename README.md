# MyApiTools

一个轻量的 API 调试工具，定位和 Apifox / Postman 类似，但**职责边界划得很清楚**：

| 能力               | 由谁完成                         |
| ---------------- | ---------------------------- |
| 发起 HTTP 请求、接收响应  | **你的本机**（Electron 主进程，无跨域限制） |
| 保存集合 / 请求 / 环境变量 | 本机 JSON 文件                   |
| 跨设备的配置同步         | **你自己的同步服务**，只存配置，不碰任何业务接口   |
| 代理、转发、代发、录制接口流量  | **不做**，服务端在架构上就没有这个能力        |

换句话说：远端服务只保存「怎么调」的配置，永远拿不到、也不会经手你的业务请求。

同一个服务还兼任**客户端更新源** —— 你把打包好的安装包发布上去，客户端连上后就能自动发现新版本。这不改变上面的边界：服务端分发的只是本工具自己的安装包，跟你的业务流量无关。

## 快速开始

### 1. 启动桌面端

```bash
npm install       # 首次执行，会下载 Electron 运行时（约 180MB）
npm start
```

窗口打开后，空白页点「插入示例集合」可以立刻看到一组可用的示例请求。

### 2. 启动同步服务（可选，需要多设备同步时才要）

```bash
npm run server        # 默认监听 0.0.0.0:8787，数据落在 server/data/sync.db
```

然后在应用的 **设置 → 配置同步** 里填服务地址，点一下同步就会自动弹出登录 / 注册框：

```
设置 → 配置同步 → 填 http://127.0.0.1:8787
     ↓
点顶栏的同步按钮（或设置页的「登录 / 注册」）
     ↓
自动弹出登录框 → 切到「注册新账号」→ 填邮箱密码 → 注册并登录
     ↓
登录成功即自动完成第一次同步
```

同步是按账号隔离的，换一批数据就换一个账号即可。服务端管理端（只有你能用，见下节）在  
`http://127.0.0.1:8787/admin`。

想部署到自己的服务器，见 [部署同步服务](#部署同步服务)。

## 功能

### 请求调试

- 方法 / URL / Params / Headers / Body / Auth / 逐请求选项
- 请求体支持 `JSON`、`Text`、`XML`、`GraphQL`、`form-urlencoded`、`multipart/form-data`（含文件上传）、`Binary`
- 认证方式：Bearer Token、Basic Auth（UTF-8 凭据正确编码）、API Key（可放 Header 或 Query）
- 不受 CORS 限制：内网接口、自签名 HTTPS 证书（可开关校验）、非标准端口都能直接调
- 中文请求头按 UTF-8 原始字节发送（与 `curl` 行为一致），并做了 CRLF 注入防护

### 响应查看

- 状态码 / 耗时 / 大小 / 内容类型
- 响应体语法高亮（JSON / XML），可一键美化或查看原始报文
- 响应头单独一栏，`Set-Cookie` 不丢
- 耗时瀑布：DNS → TCP → TLS → 等待首字节 → 内容传输
- 二进制响应自动识别并给出 Base64
- 一键复制等价的 `cURL` 命令

### 环境与变量

- 变量优先级：**全局变量 < 环境变量 < 请求级变量**
- 任意字段支持 `{{变量名}}` 占位符，含嵌套引用（`{{host}}/{{path}}`）
- 内置动态变量：`{{$timestamp}}`、`{{$uuid}}`、`{{$isoTimestamp}}`、`{{$randomInt}}`、`{{$randomString 16}}`、`{{$datetime YYYY-MM-DD}}` 等
- URL 栏实时预览替换后的真实地址，未定义的变量会明确告警
- 变量表支持一键粘贴 / 复制 `.env` 文本

### 集合与目录树

- 任意层级文件夹，支持拖拽移动、右键重命名 / 复制 / 删除
- 树内可折叠、可搜索（`Ctrl+K`）
- 删除是软删除，会同步到其它设备

### 批量执行

- 执行范围：全部请求 / 指定文件夹（含子文件夹）/ 手动勾选
- 并发数可调（1–20），支持「失败即停」
- 实时进度条 + 汇总统计（总数 / 成功 / 失败 / 平均 / P95 / 最慢）
- 结果表可按成功/失败筛选，点开看完整响应
- 一键导出 CSV（带 BOM，Excel 不乱码）或 JSON 报告

### 历史记录

- 自动记录每次发送（方法 / URL / 状态 / 耗时 / 大小）
- 点击任意一条可恢复成新的请求继续调试
- 仅保存在本机，不参与同步

### 导入导出

- **导入**：`cURL` 命令（含浏览器「Copy as cURL」的多行折行格式）、`Postman Collection v2.x`、`OpenAPI 3` / `Swagger 2`、本工具备份
- **导出**：Postman Collection v2.1、单请求 `cURL`、完整 JSON 备份
- Postman 导出→再导入经过往返验证，结构不丢

### 配置同步

- 登录后自动双向同步，可开关自动同步
- 增量同步：推送脏实体 + 按水位拉取变更
- 冲突策略：按 `updatedAt` 后写覆盖，被覆盖方向会收到提示并用远端版本收敛
- 软删除同步：一端删掉，另一端也会消失
- 支持「全量上传」「全量下载（覆盖本机）」用于首次迁移或强制对齐

**同步范围**：集合结构、请求定义、环境与变量。  
**不同步**：历史记录、超时等偏好设置、登录令牌。

### 账号与数据隔离

同步服务是**多账号**的，每个账号的数据完全隔离 —— 你在 A 账号下的集合、请求、环境，B 账号一个都看不到。

- **首次同步自动引导登录**：在设置页填好服务地址后，第一次点同步（或顶栏同步按钮）时，如果本机没有登录凭证，会自动弹出登录 / 注册框，登录成功即继续同步，不用手动分两步走。
- **凭证失效自动回登录**：服务端返回 401/403（令牌过期、被吊销、账号被禁用）时，客户端会清掉本机失效凭证、点亮红色指示灯，并弹出登录框让你重新登录；取消登录则停在「待登录」状态，不会反复打扰。
- **账号维度限流**：登录失败次数按账号统计（5 分钟内 20 次），**成功登录不消耗配额** —— 避免有人拿你的邮箱反复试错把你锁在门外。

#### 多用户隔离：每个账号是独立的工作区目录

本机工作区按用户（Profile）隔离，不再「一份配置硬掰给多个账号」：

```
<userData>/profiles/local/       未登录（本机）工作区，常驻、永远保留
<userData>/profiles/acc-<sha1>/  某个同步账号的工作区（哈希取 服务地址|邮箱）
```

- **登录 = 切换当前激活的 profile 目录**，不是覆盖本机数据：local 永远原样保留。
- **注销 = 清当前账号令牌 + 切回 local**，账号的工作区数据保留，下次登录直接复用、无需重新拉取。
- 每个账号有自己独立的目录和水位，换账号天然互不污染，不再需要「保留 / 清空」二选一。

#### 全新用户首次登录：本机内容要不要带进账号

只有「**本地未登录内容 → 全新用户**」（本机无该账号 profile 且服务端也无任何数据）时，客户端才会弹
一次「把本机内容归属给新账号？」确认框：

| 选择   | 行为                         | 适用场景              |
| ---- | -------------------------- | ----------------- |
| 认领   | local 内容整体搬进账号、local 清空、上推新账号 | 你自己首次登录，想把已有工作带过去 |
| 不归属 | 账号从空开始，local 内容原样保留          | 只想用新账号，本机内容以后再说   |
| 取消   | 本次登录作废，什么都不动               | 点错了               |

其余情况（本机已有该账号 profile、或远端已有数据的新设备）直接切到对应目录并同步，**不弹任何确认框**。

### 客户端更新

服务端可以**发布客户端安装包**，客户端连上服务端后会自动检查有没有新版本 —— 发现新版本就下载到本地、校验 sha256、然后唤起系统安装程序。

- **触发时机**：应用启动后（已连接服务端时）静默查一次；也可以手动点「帮助 → 检查更新」或设置页里的「检查更新」。
- **检查更新需要登录**：`/api/releases/latest` 与安装包下载都要求同步账号令牌，避免版本号和安装包被随便拉走。没登录时设置页会直接说明「待登录」，登录后自动补查一次。
- **只下当前平台的包**：客户端会带上自己的 `platform` / `arch`（如 `win-x64`、`mac-arm64`），服务端只返回匹配格子的版本。
- **完整性校验**：边下边算 sha256，与发布时记录的摘要比对，不一致就丢弃重来，绝不起安装程序。下载先落 `.part` 临时文件，校验通过才原子改名。
- **不做静默升级**：Windows / macOS 对替换运行中的程序有签名要求，本项目没有代码签名证书，所以只做到「下好 + 唤起安装器」，最后由你点确认。
- **可以跳过某个版本**：更新窗里点「跳过此版本」后，启动时不再为它提示；设置页会保留一条「已跳过 vX.Y.Z」并给出「恢复提示」按钮。

更新相关偏好存在 `settings.update`：

| 字段                                 | 说明               |
| ---------------------------------- | ---------------- |
| `enabled`                          | 是否在启动时自动检查       |
| `channel`                          | 更新渠道，默认 `stable` |
| `ignoredVersion`                   | 被跳过的版本号          |
| `lastCheckAt` / `lastKnownVersion` | 上次检查时间与查到的版本     |

## 部署同步服务

服务端零外部依赖 —— 只用 Node 22 内置的 `http` 和 `node:sqlite`，**不需要 npm install**。

### 直接跑

```bash
cd server
node server.js
```

环境变量：

| 变量                 | 默认值                      | 说明                                                      |
| ------------------ | ------------------------ | ------------------------------------------------------- |
| `PORT`             | `8787`                   | 监听端口                                                    |
| `HOST`             | `0.0.0.0`                | 监听地址                                                    |
| `DB_FILE`          | `./data/sync.db`         | SQLite 文件路径                                             |
| `TOKEN_TTL_DAYS`   | `30`                     | 登录令牌有效期                                                 |
| `ADMIN_TOKEN`      | 自动生成                     | 管理端令牌，显式指定时优先于令牌文件                                      |
| `ADMIN_TOKEN_FILE` | `./data/admin-token.txt` | 令牌文件路径（首次启动自动生成，POSIX 下 `chmod 0600`；Windows 不强制，靠目录权限） |
| `ADMIN_DISABLED`   | `0`                      | 设为 `1` 可彻底关掉管理端                                         |
| `ADMIN_LOCAL_ONLY` | `1`                      | 默认只允许本机回环地址访问管理端                                        |
| `ADMIN_ALLOW`      | 空                        | 管理端来源白名单，逗号分隔；`*` 表示不限来源                                |
| `RELEASES_DIR`     | `./data/releases`        | 客户端安装包存放目录（跟随 `DB_FILE` 所在目录）                           |
| `RELEASE_MAX_MB`   | `500`                    | 单个安装包体积上限（MB）                                           |
| `RELEASE_CHANNEL`  | `stable`                 | 默认发布渠道                                                  |

> 注意 `RELEASES_DIR` 默认跟随 `DB_FILE` 的目录。只改 `DB_FILE` 不改它，安装包会跟着数据目录一起搬到新位置 —— 老安装包虽然还在旧目录里，但服务端已经不再认识它们，管理页会显示为空。

> **`ADMIN_LOCAL_ONLY` 和 `ADMIN_ALLOW` 是一对，改一个不够。** `ADMIN_LOCAL_ONLY=0` 只是「解除回环限制」，真正决定放不放行的是 `ADMIN_ALLOW` 白名单 —— 白名单为空时它是空集，除回环外所有来源一律 404。这个组合的症状是「管理端打不开」，和「管理端没启用」长得一模一样。容器部署必然踩到（容器内来源 IP 是 docker 网桥地址，不可能是回环），所以 Dockerfile 里两个都设好了；裸机远程访问时也要两个一起写。服务端启动时会检测并打印告警。

### Docker

**自己构建镜像：**

```bash
cd server
docker compose up -d
```

数据落在 `server/data/`，升级镜像不丢。这份 compose 用 `build: .` 现场构建，适合开发时改完代码立刻验证。

**用发布好的镜像部署**（不需要源码，也不构建）：见 [`server/deploy/`](server/deploy/) —— 一份只含 `image:` 的 compose 加一份完整的部署说明（局域网/公网暴露、SSH 隧道访问管理端、备份、升级回滚、常见问题）。

**构建并推送到 Docker Hub：**

```bash
cd server
./build-push.sh          # Linux / macOS
.\build-push.ps1         # Windows PowerShell
```

镜像名 `myzhouye/myapitools-server`（Docker 要求仓库名全小写），tag 取 `server/package.json` 的版本号。脚本会在推送前查 Docker Hub，行为由版本号形态决定 —— 详见下面的[版本号规则](#版本号规则)：

- **正式版**（`1.2.0`）：这个 tag 已存在时会让你选择**升版本号**（patch/minor/major/手填，会写回 `package.json`）、**强制覆盖**或中止；并同时更新 `latest`。
- **开发快照版**（`1.2.0-dev`）：同一 tag 已存在时**直接覆盖、不再询问**，且默认**不动 `latest`** —— 免得 `docker pull :latest` 的人静默拿到开发中的构建。

```bash
./build-push.sh --dry-run      # 只检查与提示，不构建不推送
./build-push.sh --force        # 跳过存在性检查，直接覆盖
./build-push.sh --no-latest    # 只推版本 tag，不动 latest
./build-push.sh --latest       # 快照版也更新 latest（默认只有正式版才动）
./build-push.sh --yes          # 不提问，正式版有冲突即失败退出（CI 用；快照版照常覆盖）
```

脚本**只在 push 真的成功之后才会说「发布完成」**。推送被拒（没登录 / 没写权限）或网络中断时，它会明确报出
**「本地最新镜像没有推送到远端」**，并说清后果（远端仍是上一次推送的内容、部署端 `docker compose pull` 会报
`not found` 或拉到旧内容），最后以非零码退出。`--dry-run` 的收尾也只说「预演结束」，不会伪装成发布成功。

> **「本地构建成功」不等于「远端已有」。** `docker compose up -d` 在本地已存在该镜像时**不会**去远端拉
> （compose 默认 `pull_policy: missing`），所以本地构建后直接 `up` 能起来，并不能说明别人 `pull` 得到。
> 想确认远端到底有没有，跑一次 `docker compose pull`；或看 `build-push` 结尾有没有 `✓ 已推送`。

## 服务端管理端

服务端自带一个**只给自己用**的管理页面，有五个区块：服务总览、新建同步账号、同步账号管理（禁用 / 重置密码 / 吊销令牌 / 删除）、**客户端发布**、以及一份管理操作审计日志。

```bash
npm run server
# 启动日志里会直接打印管理端地址和令牌：
#   管理端   http://127.0.0.1:8787/admin
#   管理令牌 xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

浏览器打开 `/admin`，把令牌粘进去即可。令牌也会落在 `server/data/admin-token.txt`（POSIX 下 `0600`），**这个文件绝不能提交到版本库** —— `.gitignore` 已经把它挡掉了。

> 忘了令牌？看启动日志，或者直接 `cat server/data/admin-token.txt`。

### 安全策略：四道锁

管理端刻意做得「不好用」，因为它手里握着全部账号：

| 锁          | 做法                                                                              | 效果                     |
| ---------- | ------------------------------------------------------------------------------- | ---------------------- |
| 1. 不暴露存在性  | `ADMIN_DISABLED=1` 时，`/admin` 与 `/api/admin/*` 一律返回 **404**                     | 外人看不出这台机器有没有管理端        |
| 2. 独立令牌    | 32 字节随机令牌（`crypto.randomBytes`），比对用 `crypto.timingSafeEqual` 恒定时间比较；与用户令牌体系完全分离 | 猜不出、也测不出令牌；用户令牌换不到管理权限 |
| 3. 来源限制    | `ADMIN_LOCAL_ONLY=1` 时只认回环地址（含 IPv4-mapped IPv6 还原）；要远程访问得显式写 `ADMIN_ALLOW`     | 即使令牌泄露，公网也直接 404       |
| 4. 限流 + 审计 | 管理接口单独限流；被拒绝的请求按 `IP + 动作` 去重后写审计（60 秒内只记一条）                                    | 暴力尝试会被记录，日志又不会被刷爆      |

几条连带的安全细节：

- **管理页面本身不内嵌令牌**，只做静态页面 + 让用户手输，避免页面被缓存或被别人看到就等于泄露。
- 管理员**禁用账号或改密码会立即吊销该账号所有令牌**，在线设备下一次同步就会被踢回登录框。
- 审计只记录「谁在什么时候做了什么」，不记录任何请求配置内容。
- 推荐做法：管理端只在需要时临时开、`ADMIN_LOCAL_ONLY=1` + SSH 隧道访问，平时 `ADMIN_DISABLED=1`。

### 发布客户端新版本

管理页的「客户端发布」区块负责把安装包挂上去：

1. 选一个构建好的安装包文件（NSIS `.exe` / `.dmg` / `.AppImage` 等），页面会**从文件名推断版本号、平台和架构**（如 `MyApiTools-Setup-1.2.0-x64.exe` → `1.2.0` / `win` / `x64`）；带 `-dev` 的文件名同样认（`MyApiTools-Setup-1.2.0-dev-x64.exe` → `1.2.0-dev`）。推断只是替你省事，推错了可以手改。
2. 填更新说明（会原样显示在客户端的更新窗里），点「发布」。
3. 上传是**原始字节流**（`PUT` + query 传元信息），边收边算 sha256，带进度条。同一个「渠道 + 版本 + 平台 + 架构」再发一次就是**覆盖**，会先弹确认。

客户端查的是 `/api/releases/latest?platform=&arch=&channel=&current=`：服务端按版本号**逐段比较**（不是文本排序 —— `1.10.0` 比 `1.9.0` 新），取该格子里版本最高的一个，并与客户端上报的 `current` 比对得出 `updateAvailable`。

几条实现上的取舍：

- 服务端**从未发布过任何版本**时返回的是 `latest: null, upToDate: true`，不是错误 —— 客户端把它当「已是最新」处理，不弹窗。
- 下载走 `/api/releases/download/:id`，文件名经过 `basename` + 控制字符清洗，防路径穿越；中文文件名用 RFC 5987 的 `filename*` 传。
- 上传超过 `RELEASE_MAX_MB` 时，服务端会**先把 body 收完再回 413** —— 直接掐断连接的话客户端只会看到「连接被重置」，拿不到错误信息。超限和写失败都会清掉半截文件。
- 记录还在但磁盘文件被别人删了，下载返回 `410 GONE`（区别于记录不存在时的 `404`）。

### 放到公网的建议

服务端本身不做任何鉴权之外的花哨保护，直接暴露到公网请至少做到：

1. 前面挂一层 Nginx / Caddy，启用 HTTPS
2. **把 `/admin` 与 `/api/admin/` 在网关层直接挡掉**（管理端只走内网）
3. 限制来源 IP 或加一层基础认证
4. 定期备份 `data/sync.db`

应用侧支持 `https://` 地址。若使用自签名证书，改用 `http://` 或在服务端配置受信任证书。

## 打包桌面安装包

```bash
npm i -D electron-builder
npm run dist
```

产物在 `dist/`。配置见 `electron-builder.yml`，Windows 下会同时产出 NSIS 安装包与免安装的 portable 版本；同步服务端源码会一并放进安装目录的 `resources/server`。

安装包命名形如 `MyApiTools-Setup-1.2.0-x64.exe` / `MyApiTools-1.2.0-arm64.dmg` —— **版本、架构、平台都在文件名里**，管理页的「客户端发布」就是靠它自动推断这三个字段的，所以别改 `artifactName` 模板，否则每次发布都要手填。

### 版本号规则

「版本」在这个项目里有三个互不相干的概念，别混：

| 概念 | 唯一来源 | 谁在用 |
| --- | --- | --- |
| **客户端版本** | 根目录 `package.json` 的 `version` | electron-builder 写进安装包文件名；客户端上报给服务端的 `current` |
| **服务端版本** | `server/package.json` 的 `version` | 启动横幅、`/api/health`、管理页版本 chip、镜像 tag |
| **某个已发布安装包的版本** | `releases` 表的 `version` 列 | 发布时按安装包文件名解析 —— **真正决定「客户端算不算旧」的就是它** |

服务端版本号只有两种形态：

| 形态 | 含义 | 镜像 tag 已存在时 | `:latest` |
| --- | --- | --- | --- |
| `x.y.z` | **正式版** —— 发布出去内容就不再变化 | 停下来问你（升版本号 / 强制覆盖 / 中止）；`--yes` 下直接判失败 | 更新 |
| `x.y.z-dev` | **开发快照版** —— 内容随时可能被覆盖重推（带序号 `x.y.z-dev.N` 规则相同） | 直接覆盖、不再询问；`--yes` 也能跑通 | **不动**（确实需要就加 `--latest`） |

同一套规则落在三个地方，行为一致：

- `server/build-push.sh` / `build-push.ps1` —— 决定要不要覆盖远端 tag、要不要动 `latest`；
- `server/server.js` —— 启动横幅标注「开发快照版」，`/api/health` 与 `/api/admin/overview` 返回 `snapshot` 字段，管理页据此显示黄色「快照版」徽标；
- `compareVersion()` —— 同号时正式版压过快照版（`1.2.0-dev < 1.2.0`），所以**跑正式版的客户端不会被同号的开发构建顶掉**；快照的版号本身更高时（如 `2.0.0-dev > 1.10.0`）它确实更新，照常提示。

只认 `-dev`：`-beta.1` 之类的其他后缀规则里没定义，一律按正式版对待 —— 宁可多问一次，也不擅自放行覆盖。

日常开发想反复推同一个 tag 给测试同事用，把 `server/package.json` 的版本号改成 `1.2.0-dev` 即可；要发正式版再去掉后缀。

**客户端版本号**（根 `package.json` 的 `version`）用同一套形态：三段 `x.y.z`，可选 `-dev` 后缀（含序号形态 `x.y.z-dev.N`）。客户端只是把版本号**原样**上报给服务端（Electron 的 `app.getVersion()` 不做任何校验），真正的格式裁判是服务端的 `parseVersion`。

由此有两条硬约束：

- **别用四段版本号**（`1.2.0.1`）。服务端只认三段，解析不了时 `compareVersion` 按「无法比较」返回 0 —— 表现是**客户端永远显示「已是最新」**，一个错都不报。细节调整请升 patch 位（`1.2.0` → `1.2.1`）。
- **`-dev` 只能表达「比同号正式版更早的快照」**（预发布段恒小于同号正式版：`1.2.0-dev < 1.2.0`），做不了「正式版之后的增量」。序号建议留在个位数：预发布段不按数字排序，`-dev.10` 会被判成比 `-dev.9` 旧。

## 已知边界

- 暂不支持 WebSocket / SSE / gRPC 调试
- 暂不支持请求前置/后置脚本与断言（当前版本聚焦调试与配置管理）
- 同步冲突采用「后写覆盖」，不做字段级三方合并
- 证书校验开关是**逐请求**生效的，关闭后仅影响该请求
- 账号体系是「一人一账号、各自隔离」，没有团队共享 / 协作权限（服务端 `users.role` 字段已预留）
- 多用户隔离是「每个账号一个独立目录」，并非「一份配置共享多个账号」；切换账号互不污染、各自保留水位（已取消旧版的「整份保留 / 整份清空」二选一）
- 管理端令牌一旦泄露就等于交出全部账号，没有二次验证；用完建议直接 `ADMIN_DISABLED=1` 关掉
- **客户端更新不做静默升级**：本项目没有代码签名证书，硬替换运行中的程序只会被系统拦下，所以只做到「下载 + 唤起安装器」，最后由用户点确认
- 安装包本身没有签名，Windows SmartScreen / macOS Gatekeeper 首次运行会拦一次，需要用户手动放行
- 检查更新与下载安装包都要求登录同步账号；服务端没发布过任何版本时，客户端显示「已是最新」而不是报错
- 服务端安装包目前只有「一个渠道 + 一个平台架构格子一份」的模型，没有灰度 / 分批发布，也不能挂多个历史版本给客户端回滚
