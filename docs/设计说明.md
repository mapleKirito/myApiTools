# MyApiTools 设计说明

面向后续维护者，说明这个工具为什么这么分层、数据怎么流、哪些地方是刻意的取舍。

---

## 1. 核心约束与由此产生的架构

需求里最硬的一条是：

> 远端服务端只用于记录和同步请求配置，不做任何接口调用的协助工作。

这条约束直接决定了架构，而不是反过来：

```
┌─────────────────────────────── 你的本机 ───────────────────────────────┐
│                                                                        │
│   ┌──────────── 渲染进程（Chromium）────────────┐                      │
│   │  界面 · 状态树 · 变量解析 · 结果渲染         │                      │
│   └──────────────────┬─────────────────────────┘                      │
│                      │ contextBridge（contextIsolation: true）         │
│   ┌──────────────────▼─────────────────────────┐                      │
│   │  主进程（Node）                             │                      │
│   │   · http-client.js  ← 真正的网络出口        │                      │
│   │   · store.js        ← 本地 JSON 持久化      │                      │
│   │   · sync-client.js  ← 只传配置文本          │                      │
│   └──────────────────┬─────────────────────────┘                      │
│                      │ 只发出「配置实体」这一个方向的流量               │
└──────────────────────┼─────────────────────────────────────────────────┘
                       │
              ┌────────▼────────┐
              │  同步服务        │  存 users / tokens / entities 三张表
              │  （自建可选）    │  没有任何出站请求能力
              └─────────────────┘
```

关键点：

- **网络出口只有一个**，在主进程 `http-client.js`。渲染进程永远不直接发业务请求。
- **主进程发请求而不是渲染进程**，因为 Chromium 的同源策略在渲染进程里绕不过去。用 Node 的 `http/https` 直接发，CORS、内网地址、自签名证书、非标端口全都不再是问题。
- **同步服务在架构上就没有代理能力**：它没有 URL 白名单、没有出站 HTTP 调用、没有转发逻辑，只做 `entity` 的存取和分发。这不是「我们承诺不做」，而是「它做不到」。

## 2. 进程与模块职责

### 主进程

| 文件 | 职责 |
| --- | --- |
| `main.js` | 窗口生命周期、`app://` 自定义协议、所有 IPC 路由、应用菜单 |
| `http-client.js` | 请求构造与发送、重定向、解压、字符集解码、错误归一化 |
| `profile.js` | 多用户 Profile 管理（`ProfileManager`）：`profiles/local/` 常驻未登录工作区 + `profiles/acc-<sha1>` 每账号一目录；登录=切换激活目录、注销=切回 local 并保留账号数据、local 内容认领给新账号 |
| `store.js` | 分区存储（`WorkspaceStore`）：profile 目录内 `collections/requests/environments/globals/history/meta`.json，只重写脏分区，快照备份（保留近 5 份），旧单文件 `workspace.json` 自动拆分区 |
| `sync-client.js` | 同步服务 HTTP 协议封装、错误信息人性化 |
| `update-client.js` | 更新协议客户端：查最新版本、流式下载 + sha256 校验、`.part` 原子改名 |

### 渲染进程

| 文件 | 职责 |
| --- | --- |
| `app.js` | 入口：布局、标签页、面板挂载、快捷键、导入导出弹窗 |
| `state.js` | 单一状态树、防抖落盘、脏标记、软删除、同步序列化 |
| `vars.js` | `{{变量}}` 解析、动态变量、请求编译（配置态 → 可执行态） |
| `runner.js` | 单发 / 批量执行、并发控制、结果统计、CSV 导出 |
| `sync.js` | 同步编排、冲突处理、自动同步调度 |
| `update.js` | 更新编排：启动静默检查、下载、唤起安装器、跳过版本 |
| `importers.js` | cURL / Postman / OpenAPI 解析与反向导出 |
| `ui/*` | 各面板视图，纯 DOM 渲染 + 事件委托 |

## 3. 为什么不用打包器

渲染进程是**原生 ES Module + 自定义协议**，没有 Vite / Webpack。

原因：

- `file://` 下 Chromium 会因为 CORS 拒绝加载 ES Module，而注册一个 `standard + secure` 的自定义协议（`app://`）就能解决，代价只有 `main.js` 里二十来行。
- 少一层构建，改完代码 `Ctrl+R` 就能看到效果，调试路径最短。
- 依赖为零，不存在「半年后 npm install 装不上」的问题。

代价是界面代码要自己组织。所以 `ui/` 下按面板拆文件，模板用带自动转义的模板字符串（`ui/dom.js` 的 `html` 标签），事件统一走委托，避免手写 DOM 拼接时到处漏转义。

## 4. 数据模型

### 本地工作区（按 Profile 分区存储）

工作区按用户（Profile）隔离到不同子目录，主进程持有唯一写入口，渲染进程只通过 IPC 读写：

```
<userData>/profiles.json            { active, profiles: [...] }
<userData>/profiles/local/         未登录（本机）工作区，常驻、永远保留
<userData>/profiles/acc-<sha1>/    某个同步账号的工作区（哈希取 serverUrl|email）
```

每个 profile 目录内的数据形态如下（`WorkspaceStore` 的 `EMPTY_WORKSPACE()`）：

```jsonc
{
  "version": 1,
  "collections": [ { "id", "name", "parentId", "sort", "createdAt", "updatedAt", "deleted" } ],
  "requests":    [ { "id", "name", "collectionId", "sort", "method", "url",
                     "params", "headers", "body", "auth", "options", "variables",
                     "description", "createdAt", "updatedAt", "deleted" } ],
  "environments":[ { "id", "name", "variables": [ {"key","value","enabled","secret"} ],
                     "createdAt", "updatedAt", "deleted" } ],
  "globals":     [ { "key", "value", "enabled", "secret" } ],
  "globalsUpdatedAt": 0,
  "history":     [ ... ],          // 仅本地
  "settings":    { ... , "sync": { ... } }
}
```

三个刻意的设计：

**软删除（`deleted: true`）而不是物理删除。**
同步要能表达「这条被删了」，物理删除在增量同步里是不可见的。

**时间戳自己是冲突判据。**
每个实体都带 `updatedAt`，同步和合并都靠它。不引入 `version` 字段是因为软删除 + 时间戳已经足够表达「谁更新」。

**`globals` 是一个整体实体而不是数组里的一条条。**
它在同步侧映射成单个 `kind: 'globals', id: 'globals'` 的实体，用 `globalsUpdatedAt` 参与比较。这样全局变量表的增删改只要一个水位，不用为每一行建 id。

### 持久化策略（分区 + 快照备份）

- 工作区拆成 6 个分区文件落在 profile 目录内：`collections.json / requests.json / environments.json / globals.json / history.json / meta.json`（`meta.json` 存 `{ version, updatedAt, settings }`）。
- **只重写脏分区**：渲染进程的改动经 IPC 回传主进程，主进程按分区标记 `dirty`，`flush` 时只对脏分区做 `tmp + rename` 原子替换，避免「改一个请求就整文件重写」的 I/O 放大。
- **快照备份改为按需**：不再每次 flush 都整文件 `copyFile`；改为每次 `load()` 时把上一次会话的最终态写入 `backup/snapshot-<ts>.json`，只保留最近 5 份，仅用于极端损坏（单分区读坏）时回退恢复。
- 旧版根目录单文件 `workspace.json` 与 profile 目录内残留的旧单文件，都会在 `load()` 时自动拆分/迁移进分区结构，坏文件改名留档（`*.corrupt-<ts>` / `*.imported-<ts>`），不会丢数据。
- 渲染进程每次改动走 350ms 防抖；`beforeunload` 与 `before-quit` 各兜一次落盘。

## 5. 变量解析与请求编译

这是「配置态」到「可执行态」的转换层，全部在 `vars.js`。

```
配置态 request                  变量表                    可执行 descriptor
─────────────                  ───────                   ─────────────────
url: '{{host}}{{path}}'   ┐
params: [{key,value}]     │    全局变量                  url: 'https://api.x.com/v1/users?page=1'
headers: [{key,value}]    ├─→  ↓                        headers: [[k, v], ...]
body: {...}               │    环境变量                  body: { mode, content|fields }
auth: {...}               ┘    请求级变量                timeout / followRedirects / verifyTls
```

解析顺序（低 → 高）：全局变量 → 环境变量 → 请求级变量。

几个实现细节：

- **递归展开**：替换后如果还残留 `{{...}}` 会再解一轮，最多 8 层，支持 `{{host}}` → `{{scheme}}://x` 这种链式引用。
- **动态变量延后**：`{{$uuid}}`、`{{$timestamp}}` 这类在**每次发送时**才生成，所以同一个请求重复发送不会拿到同一个值。它们不参与未定义变量告警。
- **未定义变量不静默吞掉**：原样保留在 URL 里（会被 URL 规范化成 `%7B%7B`），同时把变量名收集起来，界面上明确告警「⚠ 未定义变量：xxx」。预览栏会把 `%7B%7B` 还原成 `{{` 方便阅读，但**真正发出去的是转义后的形式**，不做美化。
- **认证不覆盖手写头**：如果用户在 Headers 里手写了 `Authorization`，认证配置不会再去覆盖它。

## 6. 同步协议

### 实体格式

```jsonc
{ "kind": "request", "id": "req_x", "updatedAt": 1730000000000,
  "deleted": false, "data": { ...完整实体... } }
```

`kind` 取 `collection` / `request` / `environment` / `globals`。

### 水位（rev）

服务端维护一个全局单调递增的 `rev`。每次写入占一个 `rev`。客户端记住 `lastRev`，`GET /api/sync/pull?since=<lastRev>` 只返回更新的部分。

用全局计数器而不是每用户计数器，是因为拉取时已经按 `user_id` 过滤了；全局计数器省掉了「按用户分配水位」的簿记，且天然单调。

一个细节：**内容没变化的重复推送不推进水位**。用户反复点保存不应该制造无意义的增量，否则每次同步都要传一堆废数据。

### 冲突解决

按 `updatedAt` 后写覆盖。

```
客户端提交 updatedAt = T_c
服务端已有 updatedAt = T_s

T_c >= T_s  → 落地，rev+1
T_s >  T_c  → 拒绝，进入 conflicts 数组
```

被拒绝时，服务端**把服务端版本的完整数据一起放进 conflicts 回传**：

```jsonc
conflicts: [{ "kind", "id", "serverUpdatedAt", "serverRev", "serverDeleted", "serverData" }]
```

这样客户端拿到响应就能直接覆盖本地并提示用户，不需要再发一次定向拉取。这个设计是为了少一次往返 —— 早期版本只回传 `serverUpdatedAt`，客户端还得自己想办法把那个版本捞回来，而如果那个 `rev` 已经低于本地水位，增量拉取根本拉不到它。

### 首次同步与全量对齐

- 首次：本地 `lastRev = 0`，全量推送（`pushAll`），再全量拉取
- 日常：只推脏实体，只拉 `rev > lastRev` 的增量
- 强制对齐：「全量下载」会以 `since=0` 拉全量并**强制覆盖本机**，界面上有二次确认

### 服务端表结构

```sql
users     (id, email, password_hash, salt, created_at, updated_at,
           role,          -- user | admin，预留给以后的管理员分级
           status,        -- active | disabled，禁用后登录与同步一律拒绝
           last_login_at, note)
tokens    (token, user_id, created_at, expires_at, device)
entities  (user_id, kind, id, data, deleted, updated_at, rev,  PK(user_id, kind, id))
rev_counter (id=1, rev)
admin_audit (id, at, ip, action, detail)   -- 管理端操作与拒绝记录
releases  (id, channel, version, platform, arch, file_name, stored_path, size,
           sha256, notes, published_at, downloads,
           UNIQUE(channel, version, platform, arch))   -- 客户端安装包目录
```

**账号隔离靠 `entities` 的主键前缀 `user_id`**：`/api/sync/*` 的每一条 SQL 都带 `WHERE user_id = ?`，而且 `user_id` 只来自令牌解析结果，不接受客户端传参。所以换一个账号登录，拉取结果天然是空的 —— 隔离是数据模型层面的，不是靠查询时记得加过滤条件。

**老库平滑升级**：`CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列，所以 `users` 新增的列走一个 `ensureColumn()`，用 `PRAGMA table_info` 查一次再 `ALTER TABLE ADD COLUMN`。这样 1.0 时代的 `sync.db` 直接拿过来跑不会炸。

### 鉴权与限流

密码用 `scrypt` 加盐派生，令牌用 32 字节随机数（64 位十六进制），比较用 `timingSafeEqual` 防时序侧信道。

限流是两层的，策略不一样：

| 维度 | 阈值 | 统计什么 |
| --- | --- | --- |
| 来源 IP | 120 次/分钟 | 所有登录尝试（防扫描） |
| 账号邮箱 | 20 次/5 分钟 | **只统计失败** |

账号维度只统计失败是有意的：如果成功登录也吃配额，攻击者拿别人的邮箱反复试错就能把对方锁在门外，等于送了一个拒绝服务入口。

鉴权失败不是笼统的 401，而是带机器可读的 `code`，客户端据此决定要不要弹登录框：

| 场景 | HTTP | code |
| --- | --- | --- |
| 没带令牌 | 401 | `AUTH_REQUIRED` |
| 令牌不存在 / 已被吊销 | 401 | `AUTH_INVALID` |
| 令牌过期 | 401 | `AUTH_EXPIRED` |
| 账号被管理员禁用 | 403 | `ACCOUNT_DISABLED` |

被静默自动同步撞上 401 时，客户端只点亮指示灯并提示一次，不弹框打断用户；用户主动点同步才会弹登录框。

## 6.5 用户体系与账号隔离

### 登录时机：由同步流程决定，而不是单独的「登录页」

用户不需要先登录再同步。流程是：

```
点同步 → 没有 serverUrl → 提示去设置页
       → 有 serverUrl 但没 token → 弹登录 / 注册框 → 登录成功 → 接着把这次同步做完
       → 有 token → 正常同步，收到 401/403 → 清本机失效凭证 → 弹框重登
```

`syncNow()` 内部用「先登录、再递归自己一次」来收口，而不是把登录状态散落在各个调用点。

几个刻意的细节：

**登录框单飞**：`ensureAuth` 用一个模块级的 `authFlow` Promise 做单飞。自动同步、顶栏按钮、设置页按钮可能同时触发，没有单飞就会叠出好几个模态框。

**登录框只收集凭据**：`ui/authModal.js` 只负责「把邮箱密码变成 token」，落盘、账号归属确认、后续同步全部在 `sync.js`。这样弹窗可以单独被复用（过期重登、换账号都是同一个组件，靠 `reason` 换标题和说明文案）。

**状态是四态而不是两态**：`off`（没配服务）/ `auth`（配了地址但没登录）/ `syncing` / `ok`。少了 `auth` 这一态，就没法区分「你还没连」和「你连了但掉登录了」。

### 多用户隔离：每个账号是一个独立 Profile 目录

旧模型「本机只存一份配置 + 一个 `accountKey` 记归属」本质是「一份数据硬掰给多个账号」，换账号时
要么污染要么清空，风险很高。现改为**物理隔离**：每个同步账号是一个独立的 profile 目录，互不重叠。

```
<userData>/profiles/local/       未登录（本机）工作区，常驻、永远保留
<userData>/profiles/acc-<sha1>/  某账号工作区（哈希取 serverUrl|email，小写）
```

- **登录 = 切换当前激活的 profile 目录**，不是覆盖本机数据：local 永远原样保留。
- 同步/请求/渲染逻辑**完全不感知 profile**，它们只读写「当前激活的 `WorkspaceStore`」；切换只在
  `flush 当前 → 改 active 指针 → load 目标` 三步里发生，单写入口不变。
- **注销（`logoutToLocal`）= 清当前账号令牌（sync.token/enabled/lastRev 清零）+ 切回 local**，
  账号 profile 数据保留，下次登录直接复用、无需重新拉取。
- 远端隔离仍是数据模型层面的（`entities` 主键前缀 `user_id`，见 §6.2）；本机隔离是文件层面的，
  两层叠加，换账号天然互不污染。

### 新用户首次登录：本机内容要不要带进账号

唯一需要用户拍板的场景是「**本地未登录内容 → 全新用户**」：本机没有该账号 profile，且服务端也没有
任何数据（register 直接算空；login 但本机无 profile → 发一次 `pull since:0` 探测，0 实体且无 hasMore
才算空）。此时弹 `confirmLocalClaim`：

- **「认领」（yes）** → `claimLocalInto(claim:true)`：把 local 的 collections/requests/environments/globals/
  history/settings 整体搬进账号 profile、local 清空，内容视作新账号内容上推。
- **「不归属」（no）** → `claimLocalInto(claim:false)`：账号 profile 从空开始，local 原有内容原样保留。
- **「取消」** → 本次登录作废，什么都不动。

其余情况（本机已有该账号 profile / 远端已有数据的新设备）直接切到对应 profile 并同步，**不弹任何确认框**。
⇒ 旧模型里「保留本机 / 清空本机」的二选一、以及 `lastRev` 与脏标记的手工清零都消失了——因为每个账号
有自己独立的 profile 目录与独立的水位，切换不会互相踩。

一个被冒烟抓出来的关键修正：`confirmLocalClaim` 只在「**当前激活的就是 local 工作区、且 local 确有内容**」
时才弹。已登录账号 A 再切到新账号 B 时，激活的是 acc-A，绝不能把 A 的内容当成 local 内容弹框，否则
切走后 A 的内容会被误判丢失。

## 6.6 管理端与安全策略

需求是「只有我自己能用这个管理」。管理端手里握着全部账号（重置密码、吊销令牌、删数据），所以它不是加个登录就完事，而是四道独立的锁：

| 锁 | 实现 | 为什么需要 |
| --- | --- | --- |
| 1. 不暴露存在性 | `ADMIN_DISABLED=1` 时统一返回 404 | 外人扫不到这台机器有没有管理端，减少被针对的面 |
| 2. 独立令牌 | 32 字节随机 + `timingSafeEqual` 比较，与用户令牌体系完全分离 | 用户令牌拿不到管理权限；恒定时间比较避免逐字节爆破 |
| 3. 来源限制 | `ADMIN_LOCAL_ONLY=1`（默认）只认回环地址，要远程得显式 `ADMIN_ALLOW` | 令牌万一泄露，公网请求还是 404 |
| 4. 限流 + 审计 | 管理接口独立限流；被拒请求按 `IP + 动作` 去重后写审计（60 秒一条） | 尝试会被记录，但日志不会被刷爆 |

令牌不放页面里，`/admin` 只返回一个让用户手输令牌的静态页；页面带 `X-Frame-Options: DENY` 与 `Content-Security-Policy`，防点击劫持。

容器部署时有个现实约束：容器内看到的来源 IP 永远是 docker 网桥地址，回环限制用不上。所以镜像里 `ADMIN_LOCAL_ONLY=0`，改由 compose 把宿主端口只绑 `127.0.0.1` 来保证不对外暴露 —— 用端口绑定换掉来源判断，安全边界更直观。

连带的两个行为：

- 管理员**禁用账号或改密码时立刻吊销该账号的全部令牌**，在线设备下一次同步就被踢回登录框，而不是等令牌自然过期。
- 审计只记「谁在什么时候做了什么」，不记任何请求配置内容。

## 6.7 客户端更新分发

需求是「客户端连上服务端后能发现自己有新版本，服务端能发布新版本」。这一节记几个不那么显然的决定。

### 为什么不做静默自动升级

Windows 与 macOS 都要求安装包有代码签名才允许替换运行中的程序，macOS 还额外要公证。本项目没有证书，硬做静默替换的结果是**用户在系统拦截弹窗里看到一堆看不懂的警告**，体验比手动点一次差得多。

所以流程停在「下载 → 校验 → `shell.openPath()` 唤起安装器」，最后一步由用户确认。客户端也**不试图替换正在运行的自己** —— 那是 `electron-updater` 这类工具配上签名后才有资格做的事。

### 版本比较不能交给 SQL 或字符串

`'1.10.0' < '1.9.0'` 在字符串比较下是 **true**，按文本排序取「最新」会拿到错的版本。服务端因此把版本号解析成分段数字逐段比较（`parseVersion` / `compareVersion`），并额外让**同号正式版压过预发布版**（`1.2.0 > 1.2.0-beta`）。发布列表的排序也是内存里排，不用 SQL `ORDER BY version`。

### 上传为什么不用 multipart/form-data

零依赖下手写 boundary 很容易出错（分片、CRLF、结尾 `--` 都要精确），收益却只是「看起来标准」。改成 **`PUT` + 原始字节流，元信息全走 query**：

```
PUT /api/admin/releases?version=1.2.0&platform=win&arch=x64&channel=stable&name=<base64url>&notes=<urlenc>
```

好处是服务端可以**边收边算 sha256**，落盘路径也是直的。中文文件名不能塞 Header（Node 的 `http` 会因非 Latin-1 字符报 `ERR_INVALID_CHAR`），所以走 base64url 编码放在 query 里。

### 超限时先读完 body 再报错

上传超过 `RELEASE_MAX_MB` 时，直觉做法是 `req.destroy()` 立刻断开。但 destroy 会把**响应也一起掐断**，客户端只看到 connection reset，根本收不到 413。正确做法是：先查 `content-length` 快速拒绝；真超了就置 `tooBig` 标记、**不再落盘但继续把 body 读完**，`end` 之后再回 413。

同样地，失败或超限时要删掉半截文件 —— 而且必须等 `ws` 关闭后再删。Windows 上句柄没释放，`fs.rmSync` 会直接 `EBUSY`。

### 下载落 `.part`，校验过再改名

客户端下载先写 `<name>.part`：

```
fetch → Readable.fromWeb(res.body) → Transform(算 sha256 + 节流进度) → createWriteStream(.part)
     → 校验 content-length 与 x-release-sha256
     → 通过：rmSync(最终路径) + renameSync(.part → 最终路径)
     → 失败：删掉 .part
```

这样中途断线、被中间人篡改、磁盘写满，都不会留下一个「看着像安装包」的坏文件，也不会覆盖掉上一次已经下好的好包。测试里专门有一条：**保持文件大小不变、只换内容**，验证 sha256 能拦住，并且旧的好包还在。

进度通过 IPC 推到渲染进程时做了 ~120ms 节流 —— 每个 chunk 都发一条会把 IPC 打爆，界面反而更卡。

### 跳过某个版本的状态放哪

`settings.update.ignoredVersion` 落盘，所以重启后依然生效。检查到新版本但命中的是被跳过的版本时，只静默放过，不弹窗。

这里踩过一个坑：「已跳过」提示原本只渲染在 `available`（有新版本）状态上。但用户完全可能**下载完之后**才去点「跳过此版本」，那时状态已经是 `downloaded`，提示和「恢复提示」按钮就永远不出现 —— 用户没有反悔的入口。修法是把这段提示的判断提到状态机外面，只要「记录的忽略版本 == 服务端最新版本」就渲染。

### 三个「版本」不是一回事，别让它们互相漂移

这个功能一进来就撞上了版本号混乱：仓库里同时存在服务端自报版本、客户端版本、镜像 tag 三个数字，各写各的，谁也不知道哪个是真的。现在收敛成两条规则：

| 概念 | 唯一来源 | 说明 |
| --- | --- | --- |
| **客户端版本** | 仓库根目录 `package.json` 的 `version` | 打进安装包文件名，也是客户端上报的 `current` |
| **服务端版本** | `server/package.json` 的 `version` | `server.js` 用 `require('./package.json').version` 取，代码里没有第二个字面量 |
| **某个已发布安装包的版本** | `releases` 表的 `version` 列 | 发布时按文件名解析出来的，与上面两者都无关 |

三者的**形态**统一为三段 `x.y.z`，可带 `-dev` 开发标记（含 `x.y.z-dev.N`），**不用四段版本号**。

理由：客户端把版本号**原样**上报（Electron 的 `app.getVersion()` 不做任何校验），格式的唯一裁判是服务端的 `parseVersion`，它只认这两种写法。四段（`1.2.0.1`）会让解析失败 → `compareVersion` 按「无法比较」返回 0 → 客户端**永远显示「已是最新」，且一个错都不报**。同理，`-dev` 这类预发布后缀恒小于同号正式版，只能表达「比正式版更早的快照」，当不了「正式版之后的增量」——那种需求升 patch 位。

管理页「客户端发布」选文件时会从文件名推断版本号（`admin.html` 的 `inferVersionFromName`）。这里踩过一个坑：直接取 `/(\d+\.\d+\.\d+(?:-[0-9A-Za-z.]+)?)/` 时，后缀那段的字符集含 `.` 和字母数字，会把架构尾巴整段吃掉 —— `MyApiTools-Setup-1.2.0-x64.exe` 推断成 `1.2.0-x64.exe`，而发布校验正则与服务端 `parseVersion` 都放它过关，于是「发布成功、版本号却是垃圾」，零报错。带 `-dev` 的文件名反而碰巧正确（后缀在 `-x64` 的那个 `-` 前就停了），所以这个坑专门咬正式版文件名。现在推断后会显式剥掉尾部平台/架构段，`test-e2e.js` 里把页面上的这个函数抠出来真跑一遍做回归。

开发用的 `server/docker-compose.yml` 里镜像 tag 是固定的 `latest` —— 那份 compose 用 `build: .` 现场构建，不进 registry 也不被 pull，写具体版本号只会多一个会漂移的数字。真正发布的镜像 tag 由 `build-push.sh` / `build-push.ps1` 从 `server/package.json` 取，不会手写。

一个连带影响：`Dockerfile` 里的 `COPY package.json` 从「占位」变成了**必需**（少了它容器启动即崩），所以在那一行上加了注释说明。

## 6.8 镜像构建、推送与部署分发

### 两类使用者，两份 compose

改代码的人和部署的人关心的事完全不同，所以拆成了两份文件：

| | `server/docker-compose.yml` | `server/deploy/docker-compose.yml` |
| --- | --- | --- |
| 用途 | 开发时改完立刻验证 | 部署到服务器 |
| 镜像 | `build: .` 现场构建 | `image: myzhouye/myapitools-server:<tag>` |
| 版本 | 固定 `latest` | 可用 `MYAPITOOLS_TAG` 固定到具体版本 |
| 附带 | —— | 一份完整部署说明（公网暴露、SSH 隧道、备份、升级回滚、FAQ） |

`deploy/` 那份刻意不带 `build:`。部署机上不该需要源码和构建缓存，`docker compose up -d` 直接拉镜像跑。

### 镜像名必须全小写

Docker 对仓库名有硬性大小写要求，`myzhouye/myApiTools-server` 会在 `docker build` 阶段直接报
`invalid reference format: repository name must be lowercase`。这个错误出现在构建输出里，
很难联想到是名字大小写的问题，所以统一用 `myzhouye/myapitools-server`（Docker Hub 上大小写
本就指向同一个仓库），两个脚本里还各加了一道前置校验，让它在动手之前就报错。

### 版本存在性检查

推之前要回答一个问题：这个版本号是不是已经发过了？答案是三态的，不是布尔值：

| 结果 | 含义 | 处理 |
| --- | --- | --- |
| `no` | 确认不存在（API 回 404） | 直接放行 |
| `yes` | 确认存在（API 回 200） | 正式版：询问升 patch/minor/major、手填、或强制覆盖；快照版：直接覆盖（见下） |
| `unknown` | 查不出来（网络不通、私有仓库、API 不可达） | 明确告知「无法确认」，再让用户决定要不要继续 |

`unknown` 这一档是刻意保留的：把「查不到」硬当成「不存在」会在网络抖动时静默覆盖已发布的版本；
硬当成「存在」又会让离线环境完全没法发布。所以降级成提问，并把理由说清楚。

主路径走 Docker Hub 的公开 API（`registry.hub.docker.com/v2/repositories/<repo>/tags/<tag>/`），
失败时用 `docker manifest inspect` 兜底；两条都不通才是 `unknown`。

升级版本号时会**写回 `package.json`** —— 服务端版本号只有这一个来源，改一处就够了，
不需要再手工同步别的地方。

提问得有个人能回答。非交互环境（CI、重定向）下先给出「改用 `--yes` 或 `--force`」的指路，
而不是打印一个读不到答案的 `[1-5, 0]` 提示、再把空输入当成「中止」。

### 版本号规则：正式版与 `-dev` 快照版

「同一个 tag 能不能被覆盖」这件事，由版本号后缀表达，不额外加开关：

| 形态 | 含义 | 镜像 tag 已存在时 | `:latest` |
| --- | --- | --- | --- |
| `x.y.z` | 正式版，发布出去内容就不再变化 | 走上面的冲突询问；`--yes` 下判失败 | 更新 |
| `x.y.z-dev` | 开发快照版，内容随时可能被覆盖重推 | 直接覆盖、不问；`--yes` 也能跑通 | **不动**（`--latest` 可强制） |

三个取舍：

- **快照版为什么不更新 `latest`**：`latest` 是给「`docker pull` 一把梭」的人用的。让它指向一个
  随时会被覆盖的开发构建，等于把不稳定版本悄悄推给所有人。要动就得显式加 `--latest`。
- **快照版为什么不做冲突询问**：`-dev` 的定义就是「内容随时可能被覆盖重推」，每次构建推同一个
  tag 正是它的用法。若也走询问，CI 里想反复推快照就得塞 `--force` —— 而 `--force` 太宽，
  会连正式版一起放行，等于把规则拆掉了。
- **只认 `-dev`**：`-beta.1` 之类的后缀规则里没有定义，一律按正式版对待。宁可多问一次，
  也不擅自放行覆盖。

服务端运行时读同一套规则（`IS_SNAPSHOT = /-dev(\.|$)/.test(VERSION)`），但**不据此改变任何
行为**，只用来把「跑的是什么」说清楚：启动横幅标注「开发快照版」并给出转正式版的做法，
`/api/health` 与 `/api/admin/overview` 返回 `snapshot` 字段，管理页据此显示黄色「快照版」徽标。
理由很实际 —— 快照版跑在正式环境上最难解释的现象就是「版本号没变，行为却变了」，先在第一眼
把它点出来。

客户端更新那侧同样受益：`compareVersion` 里「预发布段小于同号正式版」这条让 `1.10.0-dev < 1.10.0`
成立，所以**跑正式版的机器不会被同号的开发构建顶掉**；而快照的版号本身更高时
（`2.0.0-dev > 1.10.0`）它确实更新，照常提示。同号让位、高号照推。

### 管理端在容器里恒 404 的坑

容器内看到的来源 IP 是 docker 网桥地址（默认 `172.17.0.1`），不可能是回环，所以
`ADMIN_LOCAL_ONLY` 必须设为 `0`。但**只做这一步管理端依然是打不开的**：

```
ADMIN_LOCAL_ONLY=0        → 解除「仅回环」限制
ADMIN_ALLOW 为空          → 白名单是空集，除回环外一律拒绝
```

连起来的效果是 `/admin` 恒返回 404 —— 外观和「管理端根本没启用」一模一样，排查起来
会往完全错误的方向走。所以 `ADMIN_ALLOW` 必须同时给（容器里给 `*`，真正的访问边界是
「宿主端口只绑 `127.0.0.1`」+ 40 字节随机令牌）。服务端启动时如果发现这个组合会主动
打印一行告警，把该填什么直接写出来。

## 7. HTTP 执行引擎的几个取舍

`http-client.js` 用 Node 原生 `http/https` 而不是 `fetch`，原因是需要控制到这一层：

- **关闭证书校验**（`rejectUnauthorized: false`）—— 内网自签名证书是刚需
- **`agent: false`** —— 每次新建连接，保证 DNS / TCP / TLS 耗时统计是真实的，而不是复用连接的假象
- **手动处理重定向** —— 要记录完整跳转链，并按 301/302/303/307/308 的语义决定是否改写方法、丢弃请求体；跨域跳转时主动剥离 `Authorization` / `Cookie` 防凭据泄漏
- **手动解压** —— gzip / deflate / brotli 由 `zlib` 处理，同时保留原始字节数用于「传输大小」统计

### 两个踩过的坑

**1. 非 ASCII 请求头**

Node 的 `http` 模块会拒绝含中文的 header 值（`ERR_INVALID_CHAR`）。处理方式是：把非 Latin-1 字符 encode 成 UTF-8 字节，再映射回 Latin-1 字符串写出去 —— 这**正是 `curl` 的行为**，绝大多数服务端按 UTF-8 解码能拿到正确的值。

同时必须剥掉 CR/LF，否则 `X-Foo: a\r\nX-Injected: yes` 会变成请求头注入。

**2. 错误必须收敛，不能抛穿**

任何底层同步异常（非法头名、编码问题、socket 错误）都收进统一的响应对象：

```js
{ ok: false, error: { code, message, hint }, duration, timings }
```

`hint` 是给非网络专业用户看的人话，比如：

| 错误码 | 提示 |
| --- | --- |
| `ECONNREFUSED` | 目标端口拒绝连接，服务可能未启动或端口写错 |
| `ENOTFOUND` | 域名解析失败，请检查主机名或本机 DNS / hosts 配置 |
| `DEPTH_ZERO_SELF_SIGNED_CERT` | 服务端使用自签名证书，可关闭「校验证书」 |
| `ETIMEDOUT_CUSTOM` | 已超过设定的超时时间，可调大超时 |

## 8. 界面层的状态管理

没有用框架，靠三个约定维持可控：

**1. 单一状态树 + 事件总线**

`state.js` 持有唯一的状态对象，所有改动走 `commit({ kind, ids })`。`commit` 负责：打 `updatedAt` → 记脏标记 → 排盘 → 发 `change` 事件。UI 订阅事件重绘。

**2. 输入不重绘**

在输入框里打字时用 `updateRequest(..., { silent: true })` —— 依然记脏、依然排盘，但**不发 `change` 事件**，所以不会触发重绘、不会丢焦点。等 `blur` 时再发一次让树和标签栏刷新。

这是纯 DOM 方案里最容易翻车的地方：任何一次全量重绘都会让光标跳走。

**3. 面板按需渲染 + 轻量刷新**

每个标签页对应一个 `.pane`，`paneRendered` 集合记录哪些已经渲染过。已渲染的面板在 `change` 事件里只做局部更新（刷新子标签徽标、同步输入框的值），不重建 DOM。

设置页是个例外：`refreshPane` 里被**有意跳过**，因为整页重绘会打断正在输入的服务地址、超时这些数字框。代价是同步状态（已连接 / 待登录、账号、按钮）不会自己刷新，所以 `settingsView` 自己订阅 `change` / `sync-state` / `sync-status`，调 `paintSyncCard()` 只刷同步相关的几块 DOM，并且写 DOM 前先比一次文本，避免每次 commit 都触发重排。

**4. 状态更新的合并语义**

设置是一个嵌套结构（`settings.sync.*`），局部更新必须当成子对象合并：

```js
const next = { ...settings, ...patch };
if (patch.sync) next.sync = { ...settings.sync, ...patch.sync };
```

写成 `{ ...settings, ...patch }` 会把整个 `settings.sync` 换成 `patch.sync` —— 于是「往服务地址框里敲一个字」就会顺手抹掉 `token` / `email` / `accountKey`，表现成「随手改个地址就掉登录、换账号也不问归属」。这种 bug 不会报错，只会静默丢数据，所以冒烟测试里专门有一条断言盯着它。

**5. 显隐统一走 `hidden` 属性 —— 但必须有 CSS 兜底**

所有显隐（弹窗、右键菜单、搜索下拉、更新红点……）都用 `el.hidden = true / false`，不用切换 `display` 类。但浏览器给 `[hidden]` 的那条 `display:none` 来自 UA 样式表，**优先级比任何类选择器都低** —— 元素上只要有一条 `display: grid` 之类的规则，`hidden` 就彻底失效。

所以 `app.css` 开头那条 `[hidden] { display: none !important; }` 是必须的。删掉它 `#modal-root` 就会现形：它是 `display:grid` 的全屏遮罩（`inset:0` + `rgba(8,9,12,.6)` + `backdrop-filter: blur(2px)`），于是从启动起一直盖在界面上，表现是「整个界面发虚、但弹窗清晰」—— 因为弹窗就渲染在遮罩之上。整个过程中接口全 200、控制台一条报错都没有。

这个坑在服务端 `admin.html` 上先犯过一次（登录后闸门不消失，看起来像「输了令牌没反应」），客户端这次是同一个根因。冒烟测试里专门加了两条断言盯着它：一条用临时元素验证「带 `hidden` 的 `.modal-root`，计算样式必须是 `none`」，另一条扫全页所有带 `hidden` 的元素、断言它们真的不可见。

**6. 主区域渲染前必须清掉非面板节点**

`#panes` 里不只有 `.pane`：没有标签页时 `renderPanes()` 会把欢迎页（`emptyWelcome()`）直接 `innerHTML` 塞进去，那是一个**裸的 `.empty-state`，没有 `.pane` 包裹**。而 `syncPaneElements()` 的清理只按 `.pane` 匹配，于是开第一个标签页后欢迎页不会被摘掉，一直占在面板上方——`#workspace` 是纵向排列，欢迎页先把上半屏占住，真正的面板被挤到下面。

设置页是这条 bug 最刺眼的受害者（用户原话：「默认界面上的文案和新建按钮还保留着，设置内容被挤到下面了」）。修法是在清理循环之前，先把 `#panes` 里所有非 `.pane` 子节点移除。

它之前一直被上面第 5 条那个遮罩 bug 盖着：`.modal-root` 的全屏遮罩从启动起就盖在主区域上，主区域到底长什么样根本没人看见，遮罩修好后才露出来。冒烟里补了 5 条断言（欢迎页已清空、主区域无残留非面板节点、活动面板未被挤下去、设置页顶到主区域最上沿、设置页背后无残留欢迎页）——撤掉修复后恰好这 5 条报红、其余 122 项全过，说明它们盯的正是这个根因。

**7. 谁 `overflow: auto`，谁就必须满宽 —— `max-width` 只能写在不滚动的那层**

设置页原来写成 `.settings-page { max-width: 860px; padding: …; overflow: auto; }`，是全仓唯一把宽度上限写在**滚动容器**上的地方（`.subtab-body` / `.res-body` / `.runner-results` / `.env-detail-body` 都满宽）。滚动条画在滚动容器的右边缘，于是它停在 860px 处而不是主区域最右侧，右侧留一溜空白，看着像「设置页比别的标签窄一截」。

修法是拆成两层：外层 `.settings-page` 只负责滚动（`flex:1; min-height:0; overflow:auto`，满宽），内层 `.settings-inner` 负责收窄内容（`max-width:860px; padding:20px 24px 60px`）。`renderSettingsPane()` 相应套两层 div，`data-role="settings-body"` 挂到内层。内容的位置与宽度和改动前完全一致，只有滚动条回到最右侧。

这类问题不报错、不崩、功能全正常，只能靠几何守卫盯：冒烟里补了 3 条（滚动容器左右边缘与主区域对齐 / 内容仍 ≤ 860px / 内容确实挂在内层）。把 `max-width` 加回外层后恰好只有第 1 条报红。

## 9. 测试策略

```
tools/run-all-tests.js
├── check-syntax.js          语法 + 相对导入可解析 + 冒烟探针字符串语法（39 项）
├── test-http-client.js      HTTP 引擎（91 项，起本地服务器真发真收）
├── test-vars.mjs            变量解析与请求编译（58 项，打桩 window 后跑真模块）
├── test-importers.mjs       导入导出（81 项，含往返一致性）
├── test-e2e.js              同步服务端（237 项，含账号体系、管理端安全策略与安装包发布）
├── test-sync-client.js      双设备同步链路（40 项）
└── test-update-client.js    客户端更新链路（38 项，真起服务端 + 真 UpdateClient）
```

外加 `npm run smoke`：**真实启动 Electron 窗口**，在主进程注入探针，在渲染进程里模拟用户操作（点按钮、填输入框、点发送），最后断言 DOM 与真实响应。共六个阶段：

| 阶段 | 覆盖 |
| --- | --- |
| 1 | 界面骨架、请求执行、响应渲染、批量执行 |
| 2 | 配置地址 → 待登录态 → 登录框 → 前端校验 → 注册（新用户）→ 自动同步 → 弹「归属确认」选「认领」把本机内容带进账号 |
| 3 | 令牌失效 → 清凭证 → 弹「登录已过期」→ 取消后回到待登录 |
| 4 | 重新登录 → 「切换账号」确认流 → 注册另一账号 → 验证不弹旧式切换框、local 空时不误弹归属框、新账号工作区隔离 |
| 5 | 退登回本机 → 建请求 → 注册全新账号（新用户+本机有内容）→ 弹「归属确认」选「不归属」→ 验证新账号隔离、且退登后本机内容原样保留 |
| 6 | 检查更新 → 识别新版本 → 自动弹窗 → 下载 → 唤起安装器 → 卡片转「待安装」→ 跳过版本 → 恢复提示 |

阶段 6 有个顺序上的讲究：安装包是在**阶段 6 开始之前**才发布的。前面几个阶段登录后都会自动检查更新，如果那时服务端就有新版本，会平白弹出一个更新窗把它们的断言搅乱。

这一步是有必要的 —— 前面所有测试都跑在 Node 里，渲染进程的模块根本加载不了，界面层的错误一个都测不出来。冒烟测试跑在临时数据目录，不碰用户的真实配置。

两个让冒烟测试可维护的经验：

- **探针是「写在模板字符串里的代码」**，它自身的语法不在文件级语法检查里。少一个括号时 `smoke-hook.js` 照样通过，运行时整个探针静默失效。所以 `check-syntax.js` 会把六个探针抠出来单独解析。
- **每个探针用「主体函数 + 外层 try/catch」的结构**，保证任何提前 `return` 都能走到统一的结果汇总（`errorCount` / `errors`），否则「提前返回」会被默认值误报成「有未捕获异常」。探针执行另带超时，卡住时至少能报出卡在哪一阶段，而不是静默挂死。

### 测试实际抓到的 bug

| Bug | 表现 | 根因 |
| --- | --- | --- |
| `$randomString` 死循环 | 内存爆到 4GB 后崩溃 | `i < Number(len) || 12` 的运算符优先级让条件恒真 |
| 中文请求头崩溃 | `ERR_INVALID_CHAR` 抛穿主进程 | Node 拒绝非 Latin-1 头，且异常未被收敛 |
| 同步服务起不来 | `no such table: entities` | `UPDATE` 语句写在了 `CREATE TABLE` 之前 |
| 首次进环境页存不进变量 | 输入变量后无反应 | `state.envPanelId` 未初始化，写入目标为 `null` |
| DNS 耗时字段缺失 | 测试失败 | 误用 IP 字面量做断言（本来就不触发解析） |
| 改服务地址就掉登录 | 换账号时不弹归属确认，被当成「非切换」处理 | `updateSettings({ sync: {...} })` 整块替换了 `settings.sync`，顺手抹掉 `token` / `email` / `accountKey` |
| 设置页状态不刷新 | 退登后仍显示「已连接 / 切换账号」 | `refreshPane` 有意跳过设置页，但没有任何地方补一次局部刷新 |
| 成功登录也算进限流 | 攻击者可用他人邮箱把对方锁在门外 | 账号维度限流统计了所有尝试而非仅失败 |
| 冒烟测试静默挂死 | 阶段 4 卡满超时、几乎无输出 | 无显示环境下窗口被判为不可见，Chromium 把定时器钳到 1 秒起；且探针轮询按「累计次数」而非墙钟时间计时 |
| 「已跳过 vX」提示永远不出现 | 下载完再点「跳过此版本」，卡片没有任何反馈，也没有「恢复提示」按钮 | 该提示只渲染在 `available` 状态上，而下载完成后状态是 `downloaded` —— 用户没有反悔的入口 |
| 上传超限时客户端只看到「连接被重置」 | 拿不到 413 与错误码 | `req.destroy()` 会把响应一起掐断；改成超限后继续读完 body 再回 413，并先查 `content-length` 快速拒绝 |
| 「删除后下载返回 410」的测试期望写错 | 断言失败 | 删除是连记录一起删的，查不到记录自然回 404；410 只适用于「记录还在、磁盘文件被外部删掉」 |
| 容器里管理端恒 404 | `/admin` 打不开，表现和「管理端没启用」完全一样 | `ADMIN_LOCAL_ONLY=0` 只解除回环限制，真正拦截的是 `ADMIN_ALLOW` 白名单；白名单为空时它是空集，除回环外一律拒绝。容器内来源 IP 是 docker 网桥地址，必然踩到。现在 Dockerfile 两个都设（`ADMIN_ALLOW=*`），启动时还会主动打印告警 |
| 镜像名带大写无法构建 | `invalid reference format: repository name must be lowercase` | Docker 硬性要求仓库名全小写，`myzhouye/myApiTools-server` 直接不可用；统一改成 `myapitools-server`，脚本里加了前置校验以便早早报错 |
| 发布安装包后文件名是一串乱码 | 接口返回 201、发布成功，但 `fileName` 是 `3 )\ufffd_(\ufffd...` 这样的乱码，一个错都不报 | `name` 参数约定是 base64url，而 `Buffer.from(v,'base64url')` 对非法字符是**静默忽略**的，明文文件名会被解成乱码字节；乱码非空又让兜底名轮不到。改成往返校验 + 可打印性校验，明文与 base64url 两种都能正确识别 |
| PowerShell 脚本在 PS 5.1 下连解析都过不了 | `字符串缺少终止符: '@`，且报出的行号与文件实际行号差了 6 行 | 文件是 **UTF-8 无 BOM**，而 Windows PowerShell 5.1 默认按系统 ANSI 读 `.ps1`。中文被误解码后**吞掉了换行**（`-Force` 与 `-NoLatest` 两行被并成一行），here-string 的终止符随之丢失。修法是给 `.ps1` 写 UTF-8 **带 BOM**（`.sh` 相反，绝不能有 BOM，否则 shebang 失效） |
| 单行 `package.json` 读不出版本号 | 报「读不出 version」，而文件里明明有 | 读版本号用了行首锚定的正则（`^[ \t]*"version"`），只对格式化过的 JSON 有效。改成读用 JSON 解析器、写才用定点替换 |
| 升版本号时连带改掉了依赖里的同名键 | `dependencies` 里恰好有 `"version"` 时被一起改掉 | 替换没有限制次数。修法：PS 侧必须用**实例**重载 `$re.Replace($input, $evaluator, 1)` —— 静态的 `[regex]::Replace(..., 1)` 里没有「次数」参数，那个 `1` 会被绑成 `RegexOptions.IgnoreCase`（枚举值就是 1），照旧全量替换且不报错；bash 侧不用 sed 的 `0,/re/`（GNU 扩展，macOS 会报 `invalid usage of line address 0`），改用 POSIX 的 awk |
| 非交互环境下抛出一道没人能回答的选择题 | 版本冲突时打印「请选择 [1-5, 0]:」，然后把空输入当成「已中止」，退出码 1 但看不出该怎么办 | 冲突询问前没判断环境能不能交互。修法：`resolve_conflict` / `Resolve-VersionConflict` 一进来就检查，非交互直接给「改用 `--yes`（有冲突即失败）或 `--force`（直接覆盖）」的指路。`--yes` 路径不受影响（它本来就有自己的分支）。PS 侧顺带把 `[Console]::IsInputRedirected` 包进 try/catch —— 无控制台宿主里它可能直接抛 `IOException` 而不是返回 `true` |
| 客户端整个界面发虚、弹窗却清晰 | 界面像蒙了一层雾，功能全正常、控制台零报错 | `renderer/css/app.css` 缺 `[hidden] { display: none !important; }`，于是 `.modal-root` 的 `display:grid` 压过了 UA 的 `[hidden]` 规则 —— 全屏遮罩（`inset:0` + 半透明 + `backdrop-filter: blur(2px)`）从启动起一直盖着，弹窗在它之上所以清楚。与 `admin.html` 闸门不消失同一根因。这个 bug 不影响任何功能，最初 120 项冒烟全过也没抓到它，是肉眼看出来的；随后补了 2 条守卫 —— 停掉规则后恰好这 2 条报红、其余 120 项全过 |
| 开标签页后欢迎页还在，设置内容被挤到下面 | 点「设置」，主区域上半屏仍是欢迎页的文案和「新建请求」按钮，设置内容被压到下面 | 欢迎页（`emptyWelcome()`）是一个裸 `.empty-state`，被直接 `innerHTML` 塞进 `#panes`，而 `syncPaneElements()` 的清理只按 `.pane` 匹配 → 开第一个标签页时它不会被摘掉，一直占在面板上方。修法：清理前先移除 `#panes` 里所有非 `.pane` 子节点。**一直存在，只是被上一条遮罩 bug 盖住**（主区域本就看不见）。冒烟补了 5 条断言，撤掉修复后恰好这 5 条报红 |
| 设置页滚动条不贴右边 | 设置页的滚动条停在靠中间的位置，像「设置页比别的标签窄一截」 | `.settings-page` 是全仓唯一把 `max-width: 860px` 写在**滚动容器**上的地方，滚动条跟着内容宽度跑。修法：拆成「满宽的滚动容器 `.settings-page` + 收窄内容的 `.settings-inner`」。冒烟补了 3 条几何守卫，把 `max-width` 加回外层后恰好只有第 1 条报红 |

## 10. 已知取舍与后续方向

**当前不做**：

- WebSocket / SSE / gRPC 调试
- 请求前置/后置脚本、断言与测试集
- 字段级三方合并（冲突是整实体后写覆盖）
- 团队协作与权限（当前是账号级隔离，各自同步各自的）
- 客户端**静默自动升级**（没有代码签名证书，只能做到「下载 + 唤起安装器」）
- 安装包的灰度发布、分批放量、按版本回滚（当前是「一格一包、覆盖发布」）

**如果要做，优先级建议**：

1. **断言与测试**：批量执行已经跑通了，加一层断言就能变成轻量回归测试
2. **目录级权限共享**：现在 `entities` 表已经按 `user_id` 隔离，加一张 `shares` 表就能扩展到协作
3. **WebSocket 调试**：主进程加一个长连接管理器即可，架构上与同步服务无关
