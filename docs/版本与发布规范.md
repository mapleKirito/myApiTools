# 版本与发布规范

本文档约定 **main 主线、tag 版本标签、ver/ 快照分支** 三者的命名与操作流程，
以及 GitHub Actions 自动打包发布的触发规则。所有发版动作都以这里的规范为准。

---

## 1. 三类引用各自是什么

| 类型 | 命名 | 是什么 | 是否会触发打包 |
| --- | --- | --- | --- |
| **主线分支** | `main` | 可移动指针，始终指向最新代码，持续迭代 | 推送 → **仅构建不发版** |
| **版本标签** | `v<版本号>` | 钉在某次 commit 上的不可变书签 | 推送 tag → **构建 + 发 Release** |
| **快照分支** | `ver/v<版本号>` | 对应某个大/小版本的代码快照，供快速拉取与后续修复 | 推送 → **仅构建不发版** |

要点：
- **tag 和 branch 互不绑定**，都直接指向 commit。同名（如 `v1.0.0` 和 `ver/v1.0.0`）可共存，各干各的。
- tag 是**不可变**的，一旦推送就钉死在那个 commit；分支是**可移动**的，能在上面继续提交。
- 安装包文件名里的版本号取自 `package.json` 的 `version` 字段，**不是 tag 名**，所以两者必须保持一致。

---

## 2. 版本号规则（X.Y.Z）

| 段 | 含义 | 何时递增 |
| --- | --- | --- |
| X（第一段） | 大版本 | 架构性/重大变更 |
| Y（第二段） | 小版本 | 新增功能 |
| Z（第三段） | 修复版本 | 缺陷修复 |

约定：
- **新增大版本或小版本**：第三段固定为 `0`，不带 `-dev` 后缀。例：`v1.0.0`、`v1.1.0`、`v2.0.0`。
- **缺陷修复**：只递增第三段。例：`v1.0.1`、`v1.0.2`。
- **开发预览版**：在正式号后加 `-dev`。例：`v0.1.0-dev`。仅用于发布可下载的开发快照。

---

## 3. GitHub Actions 触发规则（已配置）

| 动作 | 触发结果 |
| --- | --- |
| 推送 tag `v*` | 三平台构建 → 创建/更新 GitHub Release 并上传全部安装包 |
| 推送 `main` / `dev/**` / `ver/**` 分支 | 三平台构建 → 产出 Actions artifacts（14 天），**不发 Release** |
| 手动 Run workflow | 三平台构建 → 产出 artifacts，**不发 Release** |

关键结论：**只有 tag 会消耗一个「版本号」并产生 Release。分支推送和手动触发都只是「构建验证」，不发版、不占版本号。** 见 [.github/workflows/build.yml](../.github/workflows/build.yml)。

## 4. 场景操作流程

> 以下命令在项目根目录的 PowerShell 中执行。`<USER>` 替换为你的 GitHub 用户名。

### 场景 A：新增大版本 / 小版本（X 或 Y 递增）

目标：发布 `v1.1.0`，并建立快照分支 `ver/v1.1.0`。

```powershell
# 1. 切到主线，更新版本号（第三段必须为 0，不带 -dev）
git checkout main
# 编辑 package.json，把 version 改为 1.1.0

# 2. 提交版本变更
git add package.json
git commit -m "chore: release v1.1.0"

# 3. 推送主线（只构建验证，不发版）
git push origin main

# 4. 打 tag 触发发版
git tag v1.1.0
git push origin v1.1.0          # ← 触发 GitHub Actions 构建 + 发 Release

# 5. 同步创建快照分支，供快速拉取该版本代码
git branch ver/v1.1.0 v1.1.0    # 基于同一个 commit
git push origin ver/v1.1.0      # ← 只构建不发版
```

结果：Release 页出现 `v1.1.0`；仓库有 `ver/v1.1.0` 分支可直接 clone。

### 场景 B：缺陷修复（Z 递增）

目标：基于 `ver/v1.1.0` 修一个 bug，发布 `v1.1.1`；**不新建快照分支**，快照分支 `ver/v1.1.0` 即代表该系列的最新修复版本。

```powershell
# 1. 在对应快照分支上开发修复
git checkout ver/v1.1.0
# 改代码

# 2. 更新 package.json 版本号为 1.1.1，提交
git add .
git commit -m "fix: ... (v1.1.1)"

# 3. 推送快照分支（构建验证，不发版）
git push origin ver/v1.1.0

# 4. 仅打 tag 触发发版（不新建分支）
git tag v1.1.1
git push origin v1.1.1          # ← 触发构建 + 发 Release
```

约定：`ver/v1.1.0` 分支会持续累积 `1.1.x` 的所有修复，它**始终代表 1.1 系列的最新代码**；每个具体发布点由 `v1.1.1`、`v1.1.2`… 这些 tag 标记。

> 若修复也需回灌主线，再把 `ver/v1.1.0` 合并回 `main`（`git checkout main && git merge ver/v1.1.0`）。

### 场景 C：开发预览版 / 迭代期重复构建（避免浪费版本号）

核心原则：**迭代期的重复构建不要打 tag**——tag 是正式发布点，会占一个版本号并产生不可变的 Release。

重复构建有两种正确姿势，都不消耗版本号：

1. **推送即构建**：在 `dev/**`、`ver/**`、`main` 分支上正常推送提交，每次 push 都会自动构建三平台并产出 artifacts，到 Actions 运行页下载即可。**不打 tag，不发版，不占号。**

2. **手动构建**：Actions 页 → 选中 "Build Desktop App" → Run workflow，可针对任意分支随时构建。

只有当你确实需要一个**可对外下载的开发快照**时，才打 `-dev` tag：

```powershell
git tag v0.1.0-dev
git push origin v0.1.0-dev      # ← 发一个预发布 Release（带 - 会被自动标记为 Pre-release）
```

说明：
- `-dev` tag 同样是不可变的发布点，**不要拿同一个 `-dev` tag 反复推**。需要新的开发快照时，正常迭代推分支即可（姿势 1/2），或递增 `-dev` 的版本号。
- 若确实要重做某次 dev 发布，先在 GitHub 上删掉对应 tag 和 Release，再 `git tag -d` / `git push origin :refs/tags/...` 后重新打。

## 5. 正式版与开发版：双渠道迭代

### 5.1 核心机制：用「渠道」做物理隔离

同步服务端的安装包是**按渠道（channel）存放和取最新**的（见 `releases.channel` 与 `/api/releases/latest?channel=`）。这是区分两类用户的根本支点：

| 渠道 | 给谁用 | 版本号特征 | 谁来查 |
| --- | --- | --- | --- |
| **stable** | 正式用户 | 正式号，无 `-dev`，如 `1.1.0` | 客户端默认查 stable |
| **dev** | 测试用户 | 带 `-dev`，如 `1.1.0-dev`、`1.1.0-dev.2` | 测试用户切到 dev 后查 dev |

关键性质：
- **两渠道各自独立取「最新」。** dev 频道发得再频繁、再覆盖重发，stable 频道的「最新」纹丝不动 → 正式用户**零感知**。这就是「不影响正式用户体验」的根本保障。
- 同一「渠道 + 版本 + 平台 + 架构」重复发布会**覆盖**旧包（管理端发布时会提示确认）。所以 dev 频道可以放心迭代、覆盖，不会污染 stable。
- 版本比较已支持预发布后缀：`1.1.0-dev < 1.1.0`（同号时正式版恒新于 dev 版）。

### 5.2 客户端如何决定查哪个渠道

- 本机偏好存在 `state.update.channel`，默认 `stable`，**只存本机、不参与同步**。
- 客户端更新检查时把该值传给服务端（`renderer/js/update.js` → `update-client.js`）。
- 设置页「客户端更新」卡片里有**更新渠道下拉**（正式版 stable / 开发版 dev），切换后本机持久化并即时生效。
- 偏好落在 `settings.update`，`updateSettings` 已按子对象合并，不会误伤其它字段。

> 测试用户只需在设置里把渠道切到「开发版」，之后就只从 dev 频道取更新，与正式用户完全隔离。

### 5.3 迭代关系：一条开发线，两个出口

```
日常开发 ──(频繁迭代)──▶ dev 频道：1.1.0-dev → 1.1.0-dev.2 → 1.1.0-dev.3 …   测试用户验证
                                  │
                            测试通过、功能定版
                                  │  （去掉 -dev，冻结）
                                  ▼
                       stable 频道：1.1.0                              正式用户收到更新
```

- **dev 频道 = 上游候选池**：版本号带 `-dev`，可无限迭代、可覆盖重发，只面向测试用户。
- **stable 频道 = 验证通过后的冻结快照**：版本号正式（无 `-dev`），每发一次就是一次正式更新，只增不改。
- 正式版的代码，就是「最后一个通过测试的 dev 版」去掉 `-dev` 后的同一个产物。

### 5.4 对应到 tag / 分支 / CI 的操作

**dev 迭代（给测试用户）：**
```powershell
git tag v1.1.0-dev
git push origin v1.1.0-dev          # 触发 CI 构建（带 - 自动标 Pre-release）
# 构建完成后，在服务端管理端发布时「渠道」填 dev
```
下一轮 dev 直接递增：`v1.1.0-dev.2`、`v1.1.0-dev.3`…；或对同一 dev 号覆盖重发。

**正式发布（给正式用户）：**
```powershell
# 把 package.json version 从 1.1.0-dev 改为 1.1.0（去 -dev）
git add package.json && git commit -m "chore: release v1.1.0"
git tag v1.1.0 && git push origin v1.1.0
git branch ver/v1.1.0 v1.1.0 && git push origin ver/v1.1.0
# 构建完成后，管理端发布时「渠道」填 stable
```

要点：**CI 只负责构建产物并放到 GitHub Release；「发到哪个渠道」由你在服务端管理端发布时选择。** dev 产物发 dev 频道，正式产物发 stable 频道，二者泾渭分明。

### 5.5 不影响正式用户的三条铁律

1. 一切 dev 产物只发 **dev** 频道，绝不发 stable。
2. 正式版本号（无 `-dev`）只进 **stable** 频道。
3. dev 频道可随意迭代/覆盖；stable 频道是冻结的、只增不改。

### 5.6 客户端切换（已实现）

- ✅ **设置页「更新渠道」下拉**（stable / dev）：已在「客户端更新」卡片提供，测试用户切一次即本机持久化、即时生效。见 [settingsView.js](../renderer/js/ui/settingsView.js) 与 [state.js](../renderer/js/state.js) 的 `updateSettings`。
- ⏳ 可选增强：**dev 构建默认 dev 频道**——打包时若 `package.json` 版本带 `-dev`，客户端默认 channel=dev，省去测试用户手动切换。需要可再加。

## 6. 发版检查清单

- [ ] `package.json` 的 `version` 与将要打的 tag 号一致。
- [ ] 新增大/小版本时，第三段为 `0` 且无 `-dev`。
- [ ] tag 与快照分支同名时，推分支用全写 `refs/heads/ver/vX.Y.Z`，避免与 tag 混淆。
- [ ] 推 tag 前，先推过对应分支确认三平台构建通过（Actions 全绿）。

## 7. 快速参考

| 目的 | 命令 |
| --- | --- |
| 拉取某版本代码 | `git clone -b ver/v1.1.0 https://github.com/<USER>/myApiTools.git` |
| 查看所有 tag | `git tag` |
| 查看某个 tag 指向的提交 | `git rev-list -n 1 v1.1.0` |
| 撤销本地未推送的 tag | `git tag -d v1.1.0` |
| 删除远端 tag（极少用） | `git push origin --delete v1.1.0` |
